# 人物画像フィルター Webアプリ

人物写真をローカルファイルまたはWebカメラから取り込み、アニメ調・水彩風などの簡易フィルターを **端末内だけで** 高速に適用し、加工済み画像をダウンロードできるWebアプリです。

生成AIやクラウド推論は使用せず、WebGL2フラグメントシェーダーによる複数パスの画像処理でスタイルを作り出します。

## プライバシー方針

- 画像処理はすべてブラウザ内（WebGL2 / Canvas 2D）で完結します。
- 画像データを `fetch` / `XMLHttpRequest` / `WebSocket` 等で外部へ送信することは一切ありません。
- 入力画像を LocalStorage・IndexedDB・Cache Storage へ永続保存しません。ページを再読み込みすると画像は破棄されます。
- カメラ映像は撮影プレビュー以外の用途には保存しません。撮影・キャンセル・画面遷移のいずれでも `MediaStream` のトラックを必ず停止します。
- Service Worker はアプリ本体の静的アセット（JS/CSS/HTML/マニフェスト/アイコン）のみをキャッシュし、画像データは一切キャッシュしません。
- 外部フォント・外部画像・CDNスクリプト・解析タグ（Google Analytics等）は使用していません。

## 対応ブラウザ

- 主対象：最新版の Chrome / Edge（WebGL2必須）
- 可能な範囲で対応：Safari / Firefox（最新版であればWebGL2対応）
- WebGL2非対応環境では、機能を使わせず「WebGL2に対応していません」という明確な非対応メッセージを表示します（Canvas 2Dへの機能フォールバックは実装していません。理由は「実装方針・既知の制約」を参照）。
- カメラ機能は `navigator.mediaDevices.getUserMedia` が必要なため、HTTPS接続または `localhost` でのみ利用できます。

## 実装したフィルターと処理パス一覧

すべてのフィルターは `src/filters/*.ts` で `FilterDefinition`（パラメータ定義 + シェーダーパス列）として宣言し、`src/rendering/WebGLRenderer.ts` の汎用パイプラインが実行します。各パスは前パスの出力（`uSource`）・元画像（`uOriginal`）・任意の他パス出力（`extraInputs` 経由）をサンプリングできます。

実写の人物写真（一人）を前提に構成しています。系統は「実写補正」と「画風変換」の2つです。

| フィルター | 系統 | 処理パス | 調整項目 |
| --- | --- | --- | --- |
| オリジナル | 基準 | identity（等倍コピー） | なし |
| ナチュラル美肌 | 実写 | 輝度を3帯域（低周波=陰影／中間帯=ムラ／高周波=毛穴）に分離し、**中間帯だけ**を弱める。OKLab a/b は輝度よりはるかに強く平滑化。テカリ抑制。詳細は下記 | 肌の均一さ・赤み/くすみ除去・テカリ抑制・質感キープ・明るさ |
| シネマティック | 実写 | grade（線形空間でフィルミックトーンカーブ）→ bloomCut/H/V（赤寄りハレーション、1/4解像度）→ tone（OKLabスプリットトーン）→ finish（解像度非依存グレイン+ビネット） | 露出・コントラスト・色温度・彩度・ハレーション・スプリットトーン・粒子・周辺減光・モノクロ |
| ロトスコープ | 画風 | denoise → tensor → tensorBlur → flow（構造テンソル固有分解）→ kuwahara×2（異方性）→ quantize（OKLab）→ dog → line（フロー方向へのにじませ）→ composite。詳細は下記 | 色面の平坦さ・色の段数・線の太さ・線の濃さ・彩度 |
| 水彩 | 画風 | 線形色空間+OKLabで色面整理→顔料濃度/水分量マップ→異方性にじみ×2反復→境界沈着/カリフラワー→輪郭選択復元→紙の高さマップ相互作用→最終合成 | 効果の強さ・にじみ・顔料・紙目・ディテール |
| コミック | 画風 | posterize → edge → halftone（回転網点） | 効果の強さ・網点サイズ・コントラスト |
| デュオトーン | 画風 | duotone（輝度→2色グラデーションマッピング、5配色プリセット） | 効果の強さ・配色プリセット・コントラスト |

紙目・粒子・網点・線のゆらぎはすべて `fbm`/`hash21` によるプロシージャル生成で、画像アセットは一切使用していません。

**プリセット**：`FilterDefinition.presets` で複数パラメータをまとめて切り替えます。美肌（ナチュラル/しっかり/グロウ）、シネマティック（ティール&オレンジ/ウォームフィルム/モノクローム）、ロトスコープ（写実ロトスコープ/アニメ調/グラフィックノベル）、水彩（淡彩ポートレート/にじみ水彩/濃彩イラスト）。

### 削除したフィルターとその理由

実写の人物写真で検証した結果、以下は効果が薄いか破綻していたため削除しました。

- **セルアニメ**：平滑化が弱すぎて（9タップ・半径1.5）実写の肌を平坦化できず、量子化が肌の「ノイズ」を posterize して斑になっていた。RGBチャンネル別量子化のため肌に色相フリンジも出ていた。→ **ロトスコープが正しい上位互換**
- **トゥーン**：セルアニメと2パスがバイト単位で同一。加えて `bandedLum / max(lum, 0.05)` が暗部で発散し、髪や瞳で色相が破綻していた
- **ソフトアニメ**：量子化なし・輪郭線の最大暗化21%で、「フィルターとして認識されない」水準
- **パステル**：実態は褪せたフィルム風のかぶりで、**シネマティック**が上位互換

アニメ調表現は失われないよう、ロトスコープに「アニメ調」プリセット（強い量子化＋太い線）を用意しています。

### 併せて修正した既存の不具合

- 全ての画風フィルターが**平滑化前の生写真**からSobelエッジを取っており、毛穴・後れ毛・JPEGノイズが「線」になっていた
- 紙目・網点・粒子の周波数が**出力ピクセル基準**で、プレビュー(1280px)・書き出し(最大4096px)・サムネイル(140px)で見た目が最大3倍変わっていた（`stableNoiseUv` で解像度非依存に）
- シェーダーのコンパイル失敗が `rendererError` に記録されるだけで**画面に一切表示されず**、壊れたフィルターが「何もしないフィルター」に見えていた
- `fbm` にオクターブ間回転がなく、紙目に格子状の模様が出ていた
- 4つのフィルターが同じバイラテラルをコピーして持っていた（`bilateral8` に集約）

## 顔領域の検出（MediaPipe Face Landmarker）

美肌・ロトスコープは「どこが肌で、どこが目・唇か」を知る必要があるため、MediaPipe Face Landmarker（478ランドマーク）を**ローカル同梱**して使用します。CDNは使いません。

- `@mediapipe/tasks-vision` を**バージョン完全固定**で依存に追加（wasmとJSグルーは対で一致している必要があるため）
- wasmは `scripts/copy-mediapipe-wasm.mjs` が `postinstall`/`prebuild` で `node_modules` から `public/mediapipe/wasm/` へコピー（SIMD版のみ）
- モデル `public/mediapipe/face_landmarker.task`（3.7MB）はnpmに含まれないためリポジトリに配置
- CSPに `'wasm-unsafe-eval'` を追加。これはWebAssemblyのコンパイルのみを許可するもので、`eval()` や `new Function()` は許可しません。**`connect-src 'self'` は変更していないため、画像が外部に出ない保証は不変です**
- ランドマークの並びは `FaceLandmarker.FACE_LANDMARKS_*` の接続リストから実行時に環状に組み立てます（インデックス直書きはモデル更新で壊れるため）
- マスクは **256px固定・正規化UVでサンプリング**するため、プレビュー／サムネイル／書き出しで作り直す必要がありません
- 推論は `delegate: "CPU"`。GPUデリゲートは**独自のWebGLコンテキストを作る**ため、本体のレンダラと競合してコンテキスト喪失を招きます

### フォールバック（必須要件）

以下のすべてで**例外を投げず、エラーも表示せず**、`uHasFaceMask = 0` のままシェーダー側の肌色ヒューリスティック（`skinLikelihood()`）に自動的に切り替わります。

- モデル／wasmが404、CSPでブロック、wasm非対応
- 顔が検出されない（風景写真も正当な入力です）
- 8秒のタイムアウト

**モデルファイルをサーバーから削除しても全フィルターが動作すること**をE2Eテストで検証しています（`network.spec.ts`）。

なお `skinLikelihood()` は抽出時に作り直しました。旧実装はRGB比と明度下限で判定しており、**濃い肌色を明度下限で切り捨てていた**ためです。現在はOKLabの**色相**帯で判定しており、肌の色調に関わらず機能します。

### 検出結果の反映方法

顔検出は**プログレッシブ**に適用されます。画像を読み込んだ時点で即座にプレビューを表示し、検出完了後にマスクを適用して再描画＋サムネイル再生成します（3.7MBのモデルロードでプレビュー表示をブロックしないため）。

また `setImage` は**同期的に前のマスクを破棄**します。これがないと、検出が終わるまでの数百msの間、前の被写体のマスクが新しい写真に適用されてしまいます。連続で画像を切り替えた場合に備え、キャンセルトークンでも保護しています。

## 水彩フィルターの設計（`src/filters/watercolor.ts`）

`watercolor_shader_filter_spec.md` の詳細仕様に基づき、11パス構成で実装しています。領域保護はシェーダー内の肌色ヒューリスティックで行っています（このフィルター自体はMediaPipeのマスクを参照していません。後から `faceSkinWeight()` に差し替えることは可能です）。**RGBA16F等の浮動小数点Framebufferは使用せず**、全パスRGBA8で実装しています（仕様書が許容するフォールバック）。

### パスと中間テクスチャ

| # | パス | 解像度 | `.rgba`格納内容 |
| ---: | --- | ---: | --- |
| 1 | `structure` | 50% | 適応半径Kuwahara(線形RGB分散基準)+OKLab明度のソフト量子化。**sRGBで格納**（8bit精度でリニア値を持ち回すと多パス経由でバンディングするため、線形/OKLab変換は各パス内で都度・一時的にのみ行う） / `.a`=生Sobelエッジ量 |
| 2 | `region` | 50% | `.r`=肌尤度ヒューリスティック、`.g`=水分量ベース値(protectionの逆数)、`.b`=OKLab明度キャッシュ |
| 3 | `pigmentWash` | 50% | `.r`=不均一な顔料濃度、`.g`=水分量(肌で減衰)、`.b`=紙沈着ムラ係数、`.a`=低彩度暗部フラグ(粒状化用) |
| 4-7 | `bleedH1/V1/H2/V2` | 50% | 勾配接線方向に偏らせた異方性ブラーを2反復（色のみ、sRGB） |
| 8 | `edgeDeposit` | 50% | 構造エッジ由来のバックラン＋水分差由来のカリフラワー効果＋暗部の顔料混色（色のみ） |
| 9 | `detailRestore` | 100% | 元画像とbaseColorの差分（DoG相当、追加パス不要）で目鼻口髪際だけ選択的に復元 |
| 10 | `paperInteract` | 100% | プロシージャル紙高さマップ（低中周波の凹凸+方向性繊維+微細ノイズ）が顔料の蓄積/欠落/ハイライト露出を制御 |
| 11 | `finalComposite` | 100% | 軽いディザ＋効果の強さ(=水彩の強さ)で元画像とミックス |

半解像度パス(1-8)と全解像度パス(9-11)が混在するため、`uOriginalTexelSize`（常に元解像度基準）を新設し、`uTexelSize`（直前パス基準、パスごとに解像度が変わる）と使い分けています。

### スコープ外とした項目（理由）

- **端末別3段階品質プリセット（高速/標準/高品質）**：既存のプレビュー(1280px)/書き出し(フル解像度)解像度分離＋半解像度パスで同等のコスト適応効果を代替しています。
- **RGBA16F Framebuffer / GPUタイマークエリ**：全パスRGBA8、計測は`performance.mark`ベースです。

### デバッグ表示

開発モード（`npm run dev`、`import.meta.env.DEV`）でのみ、複数パスを持つフィルターを選ぶとサイドパネル下部に「🐛 デバッグ表示」ボタンが現れます（水彩専用だったものを全フィルター対応に一般化しました）。任意の中間パスをプレビューキャンバスへ直接表示でき、「比較サムネイルを生成」で元画像＋各プリセットの並び比較ができます。ロトスコープの `flow` パスを表示すると、構造テンソルが平坦な肌には反応せず輪郭だけを拾っていることが視覚的に確認できます。本番ビルドではこのコンポーネントごとTree-shakingで除去されます。

## パフォーマンス

- プレビュー解像度は長辺1280px（初期値）に自動縮小し、書き出し時のみフル解像度（既定上限4096px、GPUの `MAX_TEXTURE_SIZE` でも追加クランプ）で再描画します。
- スライダー操作は `requestAnimationFrame` で1フレームに1回へ間引いています。
- シェーダープログラムはフィルター×パスごとに初回コンパイル後キャッシュし、フレームバッファもサイズ単位で再利用します（毎フレーム再生成しません）。
- Playwright + Chromium（ヘッドレス、**SwiftShaderソフトウェアレンダリング**）で1920px幅画像を計測：
  - フィルター切り替え（プレビュー解像度）：全フィルターで1ms未満
  - **実写4K（2160×3840）の等倍書き出し**：シネマティック 約1.5秒 ／ ナチュラル美肌 約4.2秒 ／ ロトスコープ 約6.6秒
  - ロトスコープは当初20秒かかっていました。異方性Kuwaharaが1サンプルごとに8セクタ全てをループしていましたが、1サンプルは必ず**隣接2セクタにしか寄与しない**（三角重みが1の分割になっている）ため2回に削減し、出力を一切変えずに約3倍高速化しています。
  - いずれも要件（初回表示5秒以内、フィルター処理1〜5秒以内）を満たしています。ただし計測環境はGPUハードウェアが無く**SwiftShader（CPUソフトウェアラスタライザ）** 上での実行のため、実機のGPUハードウェアアクセラレーション環境（本アプリの想定対象）ではこれより大幅に高速になります。
- `performance.mark("filter-render-start"/"filter-render-end")` を計測しているため、実機のChrome DevTools Performanceパネルでも `filter-render` という名前の計測区間として確認できます。フルHD書き出しの実測は、実際にGPUアクセラレーションが有効なChrome/Edgeでダウンロード操作を行い、DevTools Performanceパネルで確認してください。

## 実装方針・既知の制約

- **タイル処理は未実装**：4096px出力がGPUの `MAX_TEXTURE_SIZE` を超える場合は、そのGPU上限まで書き出しサイズを自動的に縮小します（`resolveExportSize` がクランプ）。現行の一般的なGPUは`MAX_TEXTURE_SIZE`が8192px以上のため実運用上は問題になりにくく、優先順位（3. フルHD級の解像度維持 > 6. UIの装飾）に従い、タイル分割処理は実装していません。
- **アップスケールはしない**：「長辺1920px」「長辺1280px」プリセットは、元画像がそれより小さい場合に拡大はしません（画質劣化を避けるため）。
- **Canvas 2Dフォールバックは実装していません**：WebGL2非対応環境では明確な非対応メッセージのみを表示します（優先順位1〜4を優先し、優先順位6のUI充実度は簡略化しました）。
- **PWA**：Service Workerによる静的アセットの最小キャッシュ（ネットワーク優先・オフライン時キャッシュへフォールバック）を実装し、新バージョン検知時は再読み込みを促すバナーを表示します。ビルド出力のプリキャッシュ・マニフェスト自動生成ツールは使用せず、依存追加を避けています。
- **EXIF Orientation**：`createImageBitmap` に依存せず自前のバイナリパーサで読み取り、Canvas 2D変換で焼き込んでいます（ブラウザ間の `imageOrientation` 既定値差異を避けるため）。
- **HEIC非対応**：仕様どおりMVP対象外です。

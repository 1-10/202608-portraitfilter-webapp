# 人物画像フィルター Webアプリ

人物写真をローカルファイルまたはWebカメラから取り込み、美肌・メイク・アニメ調・水彩風などのフィルターを **端末内だけで** 高速に適用し、加工済み画像をダウンロードできるWebアプリです。

生成AIやクラウド推論は使用せず、WebGL2フラグメントシェーダーによる複数パスの画像処理と、ローカル同梱の顔ランドマーク検出から作るメッシュ／マスクでスタイルを作り出します。

## プライバシー方針

- 画像処理はすべてブラウザ内（WebGL2 / Canvas 2D）で完結します。
- 画像データを `fetch` / `XMLHttpRequest` / `WebSocket` 等で外部へ送信することは一切ありません。
- 入力画像を LocalStorage・IndexedDB・Cache Storage へ永続保存しません。ページを再読み込みすると画像は破棄されます。
- カメラ映像は撮影プレビュー以外の用途には保存しません。撮影・キャンセル・画面遷移のいずれでも `MediaStream` のトラックを必ず停止します。
- Service Worker はアプリ本体の静的アセット（JS/CSS/HTML/マニフェスト/アイコン）のみをキャッシュし、画像データは一切キャッシュしません。
- 外部フォント・外部画像・CDNスクリプト・解析タグ（Google Analytics等）は使用していません。

## 対応ブラウザ

- 主対象：最新版の Chrome / Edge（WebGL2必須）
- 可能な範囲で対応：Safari / Firefox（最新版であればWebGL2対応）
- WebGL2非対応環境では、機能を使わせず「WebGL2に対応していません」という明確な非対応メッセージを表示します（Canvas 2Dへの機能フォールバックは実装していません。理由は「実装方針・既知の制約」を参照）。
- カメラ機能は `navigator.mediaDevices.getUserMedia` が必要なため、HTTPS接続または `localhost` でのみ利用できます。

## 実装したフィルターと処理パス一覧

すべてのフィルターは `src/filters/*.ts` で `FilterDefinition`（パラメータ定義 + シェーダーパス列）として宣言し、`src/rendering/WebGLRenderer.ts` の汎用パイプラインが実行します。各パスは前パスの出力（`uSource`）・元画像（`uOriginal`）・任意の他パス出力（`extraInputs` 経由）をサンプリングできます。

実写の人物写真（一人）を前提に構成しています。系統は「実写補正」と「画風変換」の2つです。

| フィルター | 系統 | 処理パス | 調整項目 |
| --- | --- | --- | --- |
| オリジナル | 基準 | identity（等倍コピー） | なし |
| ナチュラル美肌 | 実写 | 輝度を3帯域（低周波=陰影／中間帯=ムラ／高周波=毛穴）に分離し、**中間帯だけ**を弱める。OKLab a/b は輝度よりはるかに強く平滑化。テカリ抑制。詳細は下記 | 肌の均一さ・赤み/くすみ除去・テカリ抑制・質感キープ・明るさ |
| ビューティーメイク | 実写 | 顔メッシュ変位場でリサンプル → 肌3帯域（美肌と半径違いで共有）→ 髪の艶 → グロー抽出/ぼかし → 背景処理 → メイク＋コントゥア＋グロー合成。顔ランドマークから三角形メッシュを張って頂点を動かし、UV上に描いたメイクをテクスチャとして合成。詳細は下記 | 顔の形・目もと・肌の均し・質感キープ・ツヤ/透明感・メイクの濃さ・まつ毛/アイライン・髪の艶・背景の処理 |
| AIルック | 実写 | 生成AIのポートレート補正の仕上がりを再現。顔の形は変えない。肌3帯域で細かい凹凸（毛穴・小ジワ）を強く消し大きな陰影は残す → 赤み・黄みを抜く → 写真ごとに測った肌の明るさを目標値へ寄せる（暗い写真ほど大きく持ち上がる）→ 唇を明るく → 肌以外の髪・輪郭だけアンシャープ | 肌の明るさ・肌のなめらかさ・赤み/黄み除去・唇の明るさ・くっきり感（目/輪郭）・仕上がりの白さ・髪のツヤ/黒さ・ツヤの残し具合・陰影の暖かみ・頬の赤み除去 |
| シネマティック | 実写 | grade（線形空間でフィルミックトーンカーブ）→ bloomCut/H/V（赤寄りハレーション、1/4解像度）→ tone（OKLabスプリットトーン）→ finish（解像度非依存グレイン+ビネット） | 露出・コントラスト・色温度・彩度・ハレーション・スプリットトーン・粒子・周辺減光・モノクロ |
| ロトスコープ | 画風 | denoise → tensor → tensorBlur → flow（構造テンソル固有分解）→ kuwahara×2（異方性）→ quantize（OKLab）→ dog → line（フロー方向へのにじませ）→ composite。詳細は下記 | 色面の平坦さ・色の段数・線の太さ・線の濃さ・彩度 |
| 水彩 | 画風 | 線形色空間+OKLabで色面整理→顔料濃度/水分量マップ→異方性にじみ×2反復→境界沈着/カリフラワー→輪郭選択復元→紙の高さマップ相互作用→最終合成 | 効果の強さ・にじみ・顔料・紙目・ディテール |

| デュオトーン | 画風 | duotone（輝度→2色グラデーションマッピング、5配色プリセット） | 効果の強さ・配色プリセット・コントラスト |

紙目・粒子・網点・線のゆらぎはすべて `fbm`/`hash21` によるプロシージャル生成で、画像アセットは一切使用していません。

**プリセット**：`FilterDefinition.presets` で複数パラメータをまとめて切り替えます。美肌（ナチュラル/しっかり/グロウ）、ビューティーメイク（ほんのり/ナチュラル/しっかり）、AIルック（ほんのり/AIルック/しっかり）、シネマティック（ティール&オレンジ/ウォームフィルム/モノクローム）、ロトスコープ（写実ロトスコープ/アニメ調/グラフィックノベル）、水彩（淡彩ポートレート/にじみ水彩/濃彩イラスト）。

### 削除したフィルターとその理由

実写の人物写真で検証した結果、以下は効果が薄いか破綻していたため削除しました。

- **セルアニメ**：平滑化が弱すぎて（9タップ・半径1.5）実写の肌を平坦化できず、量子化が肌の「ノイズ」を posterize して斑になっていた。RGBチャンネル別量子化のため肌に色相フリンジも出ていた。→ **ロトスコープが正しい上位互換**
- **トゥーン**：セルアニメと2パスがバイト単位で同一。加えて `bandedLum / max(lum, 0.05)` が暗部で発散し、髪や瞳で色相が破綻していた
- **ソフトアニメ**：量子化なし・輪郭線の最大暗化21%で、「フィルターとして認識されない」水準
- **パステル**：実態は褪せたフィルム風のかぶりで、**シネマティック**が上位互換

アニメ調表現は失われないよう、ロトスコープに「アニメ調」プリセット（強い量子化＋太い線）を用意しています。

### 併せて修正した既存の不具合

- 全ての画風フィルターが**平滑化前の生写真**からSobelエッジを取っており、毛穴・後れ毛・JPEGノイズが「線」になっていた
- 紙目・網点・粒子の周波数が**出力ピクセル基準**で、プレビュー(1280px)・書き出し(最大4096px)・サムネイル(140px)で見た目が最大3倍変わっていた（`stableNoiseUv` で解像度非依存に）
- シェーダーのコンパイル失敗が `rendererError` に記録されるだけで**画面に一切表示されず**、壊れたフィルターが「何もしないフィルター」に見えていた
- `fbm` にオクターブ間回転がなく、紙目に格子状の模様が出ていた
- 4つのフィルターが同じバイラテラルをコピーして持っていた（`bilateral8` に集約）
- 顔マスクの4チャンネルを `putImageData` でCanvasへ書いていた。**Canvas 2Dは色を乗算済みアルファで保持する**ため、`.a`（羽根つき顔オーバル）が255未満の全域で `.r`/`.g`/`.b`（肌/目/唇マスク）が量子化されていた。マスクが持つべき柔らかい境界そのものが黙って劣化する経路だったので、補助テクスチャは生バイト列でアップロードする方式に変更（`vision/auxTexture.ts`）
- 唇の輪郭リングが**上唇だけの開いた弧**になっていた。`FACE_LANDMARKS_LIPS` は「口角から口角へ走る上弧と下弧」で公開されており、辺の向きに従って歩くと反対の口角で行き止まる。旧実装は閉じていない歩行結果をそのまま返していたため、唇マスクが半分しか無かった。無向グラフとして歩くよう修正し、外側輪郭と内側（口の開口）輪郭の2本を正しく取得している

上の2件と、羽根つけを `ctx.filter`（2Dコンテキストでは任意機能で、エンジン差がある）から決定的な箱ぼかし3回に置き換えたことにより、**顔マスクを参照する既存フィルター（ナチュラル美肌・ロトスコープ）の出力もわずかに変わります**。いずれもマスク精度が上がる方向の変化です（唇の保護領域が唇全体になり、乗算済みアルファによる量子化が無くなる）。

## 顔領域の検出（MediaPipe Face Landmarker）

美肌・ビューティーメイク・AIルック・ロトスコープは「どこが肌で、どこが目・唇か」を知る必要があるため、MediaPipe Face Landmarker（478ランドマーク）を**ローカル同梱**して使用します。CDNは使いません。

- `@mediapipe/tasks-vision` を**バージョン完全固定**で依存に追加（wasmとJSグルーは対で一致している必要があるため）
- wasmは `scripts/copy-mediapipe-wasm.mjs` が `postinstall`/`prebuild` で `node_modules` から `public/mediapipe/wasm/` へコピー（SIMD版のみ）
- モデル `public/mediapipe/face_landmarker.task`（3.7MB）と `public/mediapipe/selfie_multiclass_256x256.tflite`（16MB）はnpmに含まれないためリポジトリに配置。取得元は MediaPipe 公式の `storage.googleapis.com/mediapipe-models/`（`face_landmarker/float16/1`、`image_segmenter/selfie_multiclass_256x256/float32/1`）。どちらも Apache License 2.0（各モデルカードに記載）
- CSPに `'wasm-unsafe-eval'` を追加。これはWebAssemblyのコンパイルのみを許可するもので、`eval()` や `new Function()` は許可しません。**`connect-src 'self'` は変更していないため、画像が外部に出ない保証は不変です**
- ランドマークの並びは `FaceLandmarker.FACE_LANDMARKS_*` の接続リストから実行時に環状に組み立てます（インデックス直書きはモデル更新で壊れるため）
- マスクは **256px固定・正規化UVでサンプリング**するため、プレビュー／サムネイル／書き出しで作り直す必要がありません
- 検出は**二段**（`vision/faceSearch.ts`）。プレビュー用に縮めた画像ではなく**元解像度の画像**に対して行います
  - 段1（探索）：画像全体を長辺 256 から2倍ずつの全段で検出し、見つかった顔を全部集めて最大の顔を主役にします。検出器は入力を小さな正方形へ縮めて顔を探すため、大きすぎても（内部縮小のエイリアシング）小さすぎても落ち、通る解像度は写真ごとに違います。画像全体のどの段でも見つからない（全身写真で顔が小さすぎる）ときは、正方形の切り出し窓（短辺の100%→60%）で同じことをします
  - 段2（精密化）：主役の一辺の2倍の正方形を元解像度から切り出し、大きい段から検出し直して、同じ顔と確認できたものを返します。段2が全滅したら段1の粗い点では妥協せず「顔なし」にします
- 人物の部位（髪・顔の肌・体の肌・服）は MediaPipe Image Segmenter（SelfieMulticlass）で判定します（`vision/personSegmentation.ts`）。顔が分かっていれば頭と肩のまわりを切り出して推論し、全シェーダーから `personSeg()`／`personSegCoverage()` で引けます。色による肌判定（`skinLikelihood()` 系）は、白髪・茶色い前髪・暖色の壁を取り違えるため、届く範囲ではこちらが優先されます
- 推論は `delegate: "CPU"`。GPUデリゲートは**独自のWebGLコンテキストを作る**ため、本体のレンダラと競合してコンテキスト喪失を招きます
- 検出器（`vision/faceLandmarks.ts`）はランドマークとメッシュ位相を返すだけで、マスクや変位場の生成は呼び出し側（`vision/faceMask.ts` / `vision/faceGeometry.ts`）が行います。検出とベイクを分けたのは、ベイクだけが失敗しても（リングが退化、位相が取れない）マスクは生き残り、マスクしか要らないフィルターが影響を受けないようにするためです

### フォールバック（必須要件）

以下のすべてで**例外を投げず、エラーも表示せず**、`uHasFaceMask = 0` のままシェーダー側の肌色ヒューリスティック（`skinLikelihood()`）に自動的に切り替わります。ビューティーメイクは加えて `uHasFaceGeometry = 0` となり、**変形とメイクが丸ごと無効化され、肌とトーンと背景ぼかしだけが効く純粋な画像フィルターに退化**します。

- モデル／wasmが404、CSPでブロック、wasm非対応（セグメンテーションのモデルだけが欠けた場合は、顔マスクは効いたまま肌・髪の判定だけが色ヒューリスティックに戻る）
- 顔が検出されない（風景写真も正当な入力です）
- 8秒のタイムアウト

**モデルファイルをサーバーから削除しても全フィルターが動作すること**をE2Eテストで検証しています（`network.spec.ts`）。ビューティーメイクが最も厳しいケースです。変位場のスタンドインは**黒ではなくバイト128（=ゼロ変位）** にしています。黒を復号すると最大振幅の変位になり、「効果が出ない」ではなく「画面が壊れる」失敗になるためです。

なお `skinLikelihood()` は抽出時に作り直しました。旧実装はRGB比と明度下限で判定しており、**濃い肌色を明度下限で切り捨てていた**ためです。現在はOKLabの**色相**帯で判定しており、肌の色調に関わらず機能します。

### 検出結果の反映方法

顔検出は**プログレッシブ**に適用されます。画像を読み込んだ時点で即座にプレビューを表示し、検出完了後にマスクを適用して再描画＋サムネイル再生成します（3.7MBのモデルロードでプレビュー表示をブロックしないため）。

また `setImage` は**同期的に前のマスクを破棄**します。これがないと、検出が終わるまでの数百msの間、前の被写体のマスクが新しい写真に適用されてしまいます。連続で画像を切り替えた場合に備え、キャンセルトークンでも保護しています。

## ビューティーメイクフィルターの設計（`src/filters/beautyMakeup.ts`）

Instagram / Snow 系の「可愛く見せる」フィルターと同じ作り方です。**顔ランドマークから三角形メッシュを張り、頂点を動かして顔を変形し、UV上に描いたメイクをテクスチャとして合成**します。ぼかしや周波数分離だけでは到達できない部分（顔の輪郭・目の大きさ・リップ・まつ毛）を、幾何とテクスチャで作ります。

### レンダラに足りなかったもの

`WebGLRenderer` は `drawArrays(TRIANGLES, 0, 3)` の全画面三角形1枚しか描けません。頂点バッファもランドマーク配列を渡す口もないため、**メッシュをGPUで描く経路が存在しません**。

そこで既存の `uFaceMask`（256px固定・正規化UV）と同じ手を使い、**メッシュをCPUで解いた結果を補助テクスチャにして**、既存の全画面パスから読みます。

```text
[検出] MediaPipe 478点 ─── 1画像につき1回だけ ───┐
                                                 │
   ┌─────────────────────────────────────────────┴────────────────────────┐
   │ CPU（JS バリセントリック・ラスタライザ + Canvas2D）                  │
   │                                                                      │
   │ (a) tessellation の辺リスト → 三角形854枚を導出 → 頂点を移動 →      │
   │     「逆写像」を三角形ラスタライズ                                   │
   │        uFaceWarp 512²  RG = 顔の形の変位   BA = 目もとの変位         │
   │                                                                      │
   │ (b) ランドマークにメイクを描画 → チャンネル別に別半径でぼかし        │
   │        uMakeupA 1024²  R=リップ G=ツヤ B=チーク A=アイシャドウ       │
   │        uMakeupB 1024²  R=まつ毛 G=眉 B=コントゥア A=キャッチライト   │
   │                                                                      │
   │ 3枚とも「顔bboxを 0..1 とする矩形」で持つ = uFaceGeomRect            │
   └─────────────────────────────────────────────┬────────────────────────┘
                                                 │ 画像ごとに1回アップロード
                                                 ▼
  uOriginal ──> warp ──> 肌3帯域 ──> 髪ツヤ ──> finish ──> 出力
                  ▲         ▲                     ▲
                  │         │                     │
             uFaceWarp   uFaceMask         uMakeupA/B + 背景ぼけ
                         (warp後UVで引く)
```

**この分割が設計の要点です。** スライダーは uniform の重み係数にしか効きません。変位量はチャンネル別に分けて焼き、メイクの色と濃さはシェーダー側に置くので、**スライダー操作でCPU再計算が一切発生しません**。プレビュー・サムネイル・書き出しも同じ3枚を使い回します。

### パス構成（15パス）

| # | パス | 解像度 | 内容 |
| ---: | --- | ---: | --- |
| 1 | `warp` | 100% | 変位場でリサンプル（1タップ）。ここだけ上限を掛けない |
| 2-3 | `chromaH/V` | 50%（上限1600） | OKLab a/b のぼかし（美肌と共有） |
| 4-5 | `lumaLowH/V` | 50%（上限1600） | 低周波＝陰影と立体 |
| 6-7 | `lumaMidH/V` | 100%（上限2048） | 中間帯。低周波との差がムラ |
| 8 | `skin` | 100%（上限3072） | 3帯域再合成（クランプ付き）＋彩度低減＋全体の明度リフト＋コントゥア（符号付きマップ） |
| 9 | `hair` | 100%（上限2048） | 輝度勾配の直交方向へハイライトを引き伸ばし、暗髪領域へ加算 |
| 10 | `glowCut` | 25% | 肌のハイライトだけを抽出（ブルームの素） |
| 11-12 | `glowH/V` | 25% | 顔幅9%の半径でぼかす。狭いとソフトフォーカスの滲みになり、グローにならない |
| 13-14 | `bgH/V` | 25% | 背景デフォーカス用プレート（半径もスライダーに追従）。控えめ寄りに振っている理由は「届かないところ」参照 |
| 15 | `finish` | 100% | メイク合成＋グローのスクリーン合成＋背景の白寄せ＋効果の強さのクロスフェード＋ディザ |

帯域パスに上限を掛けているのは、帯域の半径が**顔幅に対する比**で決まるため、解像度を落としても見た目ではなく精度しか変わらないからです。12パス構成の書き出しコストを買い戻す一番安い場所です。

**効果の強さ（`uStrength`）の扱い**：変形はクロスフェードできません（変形済みと未変形を50%で混ぜると二重像になる）。そのため `uStrength` は warp パスで**変位量そのものに掛け**、`finish` は元画像ではなく **warp パスの出力**とクロスフェードします。マスク参照も同じ変位量で引かないとリップが唇からずれるため、変位UVの計算は1つの文字列（`WARP_UV`）を全パスで共有しています。

### メイクマスク（`src/vision/faceMakeupMasks.ts`）

マスクは**どこに乗るか**だけを持ち、色と濃さはシェーダーの uniform です。この分離がドラッグ中の再計算ゼロを成立させています。

- 各レイヤーは不透明な白で描き、**アルファチャンネルだけ**を読み出します（Canvasの色は乗算済みアルファのため、低アルファ域で値が信用できない）
- ぼかしは `ctx.filter` ではなく取り出した後のプレーンに掛けます。Canvasのフィルターは**現在の変換行列の空間で適用される**ため、楕円を作るための局所スケールがぼかし半径を楕円のサイズ倍してしまいます
- チーク・ハイライトは顔オーバルへ**クリップせず**、羽根つきオーバルのプレーンを掛けて減衰させます（クリップは硬い切り口なので、ぼかした後に切ると顎に線が出る）
- アイライナーはテーパー付きの多角形として描きます。Canvas 2Dにテーパーストロークは無く、目頭でゼロに細らないアイラインは黒い染みに見えます
- `uMakeupB.b` は**符号付き1チャンネル**です（128が中立、上がハイライト、下が影）。参照画像の艶は彩度ではなく**陰影（コントゥア）** から来ています。均して明るくすると立体感が失われ、いくら明るくしても平坦な白い面にしかなりません。空きチャンネルが無く、また不要でもありません — 同じ画素が「光」かつ「影」になることはないので、1チャンネルで無損失に両方持てます。影の重みはハイライトの半分以下にしています（塗った光は「艶」に見え、塗った影は「汚れ」に見えるため）

### 肌の処理

3帯域の周波数分離は美肌フィルターと**共有**（`src/filters/shared/skinRetouch.ts`）し、**帯域の半径と再合成の重みが違います**。

半径の選び方が要点です。2つの半径の間に入る周波数が「シミ」として減衰されるので、**低域側の半径が広いと顔の構造まで巻き込みます**。美肌の 6%（顔幅比）だと、小鼻の影・鼻翼の溝・顎の陰影（いずれも顔幅の 5〜15%）が全部シミ帯に入り、強く掛けた瞬間に**鼻が穴だけ残った塊になります**。このフィルターは 0.8%〜3.0% に絞り、シミ帯を毛穴と小さなムラだけに限定しました。大きな赤みは**彩度側**で落とします（彩度から落とせば立体感を失いません）。

そのうえで効いている工夫が3つあります。

- **補正量のクランプ**：帯域を定数倍すると、シミ（Lで数百分の1のずれ）と小鼻・口の線（大きなずれ）が同じ扱いになります。エッジゲートでは分離できません（小鼻の**内側**はエッジではない）。帯域を減衰させた後、**移動量そのものを ±0.035 でクランプ**します。シミ除去は無制限に強くできて、構造は残ります。
- **肌ゲートに被写体自身の明るさを使う**：肌領域（顔オーバル）だけを信じると、額にかかった前髪も「肌」になり、質感を潰して周囲の肌の色で塗りつぶすので**黒い前髪がベージュになります**。彩度で弾くと黒髪は分離できますが茶髪は分離できません。そこで画像ごとに**被写体の肌の明度中央値を実測**して uniform で渡し（赤み判定用に a/b の中央値も同時に測る）（`vision/skinTone.ts`）、それに対する相対値で判定します。絶対しきい値は「色白では動くが色黒では動かない」フィルターを作る典型的な誤りです。
- **トーンシフトは領域で切らない**：明度・彩度の全体シフトを顔オーバルで切ると、**頬と顎に継ぎ目の線が出ます**。マスクの羽根は顔幅の数%しかなく、質感の変更を隠すには十分でも、この大きさのトーン差は隠せません。彩度低減は色ヒューリスティックに従わせ、明度リフトは全画面に掛けています。参照画像も画面全体を持ち上げているので、境界を持たない方が結果としても近くなります。
- **肌の判定を顔の外へ広げる（`faceSkinWeightBroad`）**：領域マスクは顔オーバルしか無いので、強く掛けると**素の体に人形の頭が乗った絵**になります。顔だけが均されて明るくなり、首・胸元・腕は元のムラをそのまま残すためです。**この破綻は顔のクロップでは一切見えません**（参照画像が3枚とも頭部クロップなので、クロップ比較だけで詰めていると見落とします）。実機のフィルターは見えている肌全体を処理するので、オーバル判定と色だけの判定の**大きい方**を採ります。色だけの判定は実測した彩度差に依存します（肌 0.04〜0.10、無彩色の壁 0.03未満、髪 0.01未満、グレーのTシャツはほぼ0）。差は本物ですが広くはないので、暖色で彩度の高い背景は拾い得ます。オーバルは強い事前分布として残し、この判定は**足すだけ**なので、失敗の向きは「壁が少し均される」であって「顔を外す」ではありません。

| 元画像 | 0.710 | 0.057 | 0.618 | 0.098 |

| 参考B | 0.788 | 0.040 | 0.640 | 0.117 |

### 実測して分かった一番大きな勘違い：参照は顔をほとんど変形していない

顔の「小顔になった・目が大きくなった」印象は、画像を見た**誤読**でした。参照4枚のランドマークを実測した結果です。

| | 顔 幅/高 | 目幅/顔幅 | 目高/顔高 | 目の縦横比 | 唇幅/顔幅 | 唇高/顔高 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 元画像 | 0.857 | 0.200 | 0.071 | 0.412 | 0.331 | 0.110 |
| 参考A | 0.874 | 0.203 | 0.070 | 0.395 | 0.330 | 0.107 |
| 参考B | 0.876 | 0.203 | 0.070 | 0.395 | 0.329 | **0.118** |
| 参考C | 0.868 | 0.207 | 0.068 | 0.380 | **0.350** | **0.119** |

- **顔は細くなっていない。** むしろ幅/高 が 1〜2% 増（わずかに幅広）
- **目は大きくなっていない。** 目高は微減、縦横比は平たくなっている
- 実際に変わっている幾何は**唇の厚み（+8%）だけ**

「小顔・目が大きい」の正体は、トリミングの寄り・まつ毛のライン・コントゥア・光です。メッシュ変形を強く掛けるのは**参照が行かない方向へ顔を歪める**ことでした。プリセットの `顔の形` / `目もと` を1桁に落としているのはこの実測結果によるものです（スライダーは 100 まで開けてあります）。

「白飛び」に見えるとき、原因が明るさではないことがあります。**平坦さ**でも同じ見え方になります。

肌の明度分布を測ったところ、本実装の しっかり は 平均L 0.751・p90 0.838 で、**参照3枚のどれよりもハイライトが低い**（参考A/B/C の p90 は 0.851/0.883/0.866、L>0.85 の面積は 10.7/24.2/17.7% に対し本実装 1.8%）にもかかわらず、より飛んで見えていました。違いは**標準偏差だけ**です。参照は 0.094→0.101〜0.115 と**コントラストを上げ**、本実装は 0.094→0.085 と**下げて**いました。

下げていた原因は自分で入れた2つの操作です。明度リフトが `(1 - L)` 重みなので明るい画素ほどリフトが小さく上が詰まる、グローがスクリーン合成なので暗部を明部より持ち上げる。どちらも単体では正しく、どちらもコントラストを削ります。**露出ではなくコントラストを直す**のが正解で、被写体自身の実測肌明度を軸に肌のコントラストを1.55倍へ展開しています（標準偏差 0.100、参照域）。

明るさは**三重に足すと飛びます**。この肌のリフト・グローのスクリーン合成・背景の白寄せは全部明るさを上げる操作で、それぞれ妥当な値でも合計すると画面平均Lが元比 +0.12 まで上がりました（参照は +0.05〜0.07、参考Cは元より暗い −0.012）。RGBのクリップは 0.00% なので飽和検査では捕まらず、「飛んでいる」ではなく「平坦で白っぽい」として出ます。個別の係数ではなく**合計を測って**、+0.055（ナチュラル）／+0.070（しっかり）へ合わせています。

そして参照に有って実装に無かったものが1つあります。**グロー（拡散した光）** です。参照の肌は内側から光り、ハイライトが周囲に滲んでいます。周波数分離のレタッチは**引く**ことしかできないので、どれだけ強く掛けてもこれは出ません。光は**足す**必要があります。`glowCut/H/V` の3パスで、肌のハイライトだけを顔幅9%の半径でぼかし、スクリーン合成で戻しています。

### 参照に近づける順番は「置いていかれる部位」から

参照と並べると、差は強度ではなく**部位間の不整合**として出ます。輪郭と目だけ上げると、髪・背景・虹彩が元のまま置いていかれ、額だけ白い／目だけ大きい状態になって「加工が下手」に見えます。実際に一度そうなりました。

そこで先に3項目を埋めています。

| 項目 | 参照がやっていること | 実装 |
| --- | --- | --- |
| 髪 | 色ムラごと均一な艶のある黒へ描き直す | 髪領域の**明度ばらつきを深い値へ圧縮**し、艶を上に足す。彩度は0.85カット。ツヤだけ足しても茶色い根元が残り「同じ写真を加工した絵」に見える |
| 背景 | 壁がほぼ白で平坦 | **白へ向けた圧縮**。明るさ比例のリフトでは、当たっている壁が影より大きく上がって階調差が逆に強調される。参照の壁は明るいだけでなく平坦 |
| 虹彩 | 大きく暗く、輪郭が明瞭 | 目領域の暗部を落として虹彩を深くする。幾何を足さずに「大きい虹彩」に見せる分だけ。模様の描き直しは不可 |

これを埋めたうえで幾何を上げると不整合になりません。

### 段階を作るのは幾何。塗った層の方が早く壊れる

**幾何と塗った層で、耐えられる強度が全く違います。** これは実写でスライダーを振って測った結果です。

肌とメイクを固定して `顔の形` / `目もと` だけを 0→25→45→65→85 と振ると、**85/65 でも破綻しません**。顎は明確に細くなり目は明確に大きくなり、髪のシルエットは顔に付いてきて、強いフィルターを掛けた同一人物として読めます。一方で塗った層（リップ・アイメイク・コントゥア）にはその余裕がなく、レンジの1/4程度を超えると:

- 額が階調を失って**特徴の無い白い面**になる
- リップが**板**になる
- 拡大した目と合わさって**人形**に見え始める

そのためプリセットは**段階差を幾何に持たせ、塗った層はかなり低く抑えています**（`しっかり` で 顔の形 65 / メイク 30）。

過去の版で「強い設定が酷い」という判断を受けて**幾何も一緒に下げたことがありますが、これは誤りでした**。破綻していたのは塗った側で、幾何は仕事をしていました。スマホの美顔フィルターがやっていることの大半は幾何なので、そこを削ると「加工されていない」出力になります。

補足2点:

- スライダーの上限は 100 のままです。意図して踏み込みたい場合は手で上げられます
- `質感キープ` を独立したスライダーにしました。毛穴を残すか磁器肌にするかは好みの問題で、コード側が決めるべきことではないためです（100で毛穴帯を素通し＝ロウ肌になりません）

### 参照画像に届かないところ

生成AIで作った3段階の参照画像に対して、以下は原理的に到達できません。

- **髪**：参照は毛の一本ごとを描き直しています。ツヤの筋は流れ方向（輝度勾配の直交方向）への引き伸ばしで近似できますが、**存在しない毛束は生やせません**
- **背景**：人物セグメンテーションはMVP対象外のため、顔からの距離でぼかします。原理的に「人物と背景の境界」は出ません。当初は参照C相当まで強く掛けていましたが、**放射状のフォールオフを強く掛けると被写界深度ではなく滲んだビネットに見え、画面端の物（この写真では天井の照明）が潰れます**。立ち上がりを顔幅の1.6倍からに後退させ、プリセットの既定値も 6/18/32 まで下げています
- **虹彩**：キャッチライトと明度・コントラストは足せますが、虹彩の模様を描き直すことはしません
- **顔の向き**：メッシュ変形は面内の移動だけです。参照がわずかに正面へ向き直っている分は再現できません
- **参考B / 参考Cの「塗り」の水準**：リップの立体感、虹彩の描き直し、磁器肌の質感。上記「段階を作るのは幾何」を参照。幾何側は参照Cに匹敵する量まで掛けられます
- **全体の露出**：参照は画像全体を大きく持ち上げ、背景の壁がほぼ白になります。本実装のリフトは暗部を残す形（floor を髪の明度より上に置く）なので、壁の影までは飛ばしません。髪を灰色にしないことと引き換えです
- **二重の線**：参照Cは二重幅がはっきり描かれています。マスクのチャンネルを使い切っているため、独立した線としては入れていません（アイシャドウとまつ毛で近い印象までは作っています）

### 見た目の検証方法

`tests/e2e/visual-reference.spec.ts` が3プリセットを実写から書き出し、フル解像度書き出しの時間も測ります。**`samples/portrait.png` が無ければ skip します**。実在の人物写真をリポジトリに置けないため、「合成フィクスチャ（顔が写っていない）で調整したふり」をせず、置き場所だけを明示する形にしています。任意のポートレートを `samples/portrait.png` に置いて `npx playwright test visual-reference` を実行すると `samples/out/` に出力されます（`samples/` は .gitignore 済み）。

## 水彩フィルターの設計（`src/filters/watercolor.ts`）

`watercolor_shader_filter_spec.md` の詳細仕様に基づき、11パス構成で実装しています。領域保護はシェーダー内の肌色ヒューリスティックで行っています（このフィルター自体はMediaPipeのマスクを参照していません。後から `faceSkinWeight()` に差し替えることは可能です）。**RGBA16F等の浮動小数点Framebufferは使用せず**、全パスRGBA8で実装しています（仕様書が許容するフォールバック）。

### パスと中間テクスチャ

| # | パス | 解像度 | `.rgba`格納内容 |
| ---: | --- | ---: | --- |
| 1 | `structure` | 50% | 適応半径Kuwahara(線形RGB分散基準)+OKLab明度のソフト量子化。**sRGBで格納**（8bit精度でリニア値を持ち回すと多パス経由でバンディングするため、線形/OKLab変換は各パス内で都度・一時的にのみ行う） / `.a`=生Sobelエッジ量 |
| 2 | `region` | 50% | `.r`=肌尤度ヒューリスティック、`.g`=水分量ベース値(protectionの逆数)、`.b`=OKLab明度キャッシュ |
| 3 | `pigmentWash` | 50% | `.r`=不均一な顔料濃度、`.g`=水分量(肌で減衰)、`.b`=紙沈着ムラ係数、`.a`=低彩度暗部フラグ(粒状化用) |
| 4-7 | `bleedH1/V1/H2/V2` | 50% | 勾配接線方向に偏らせた異方性ブラーを2反復（色のみ、sRGB） |
| 8 | `edgeDeposit` | 50% | 構造エッジ由来のバックラン＋水分差由来のカリフラワー効果＋暗部の顔料混色（色のみ） |
| 9 | `detailRestore` | 100% | 元画像とbaseColorの差分（DoG相当、追加パス不要）で目鼻口髪際だけ選択的に復元 |
| 10 | `paperInteract` | 100% | プロシージャル紙高さマップ（低中周波の凹凸+方向性繊維+微細ノイズ）が顔料の蓄積/欠落/ハイライト露出を制御 |
| 11 | `finalComposite` | 100% | 軽いディザ＋効果の強さ(=水彩の強さ)で元画像とミックス |

半解像度パス(1-8)と全解像度パス(9-11)が混在するため、`uOriginalTexelSize`（常に元解像度基準）を新設し、`uTexelSize`（直前パス基準、パスごとに解像度が変わる）と使い分けています。

### スコープ外とした項目（理由）

- **端末別3段階品質プリセット（高速/標準/高品質）**：既存のプレビュー(1280px)/書き出し(フル解像度)解像度分離＋半解像度パスで同等のコスト適応効果を代替しています。
- **RGBA16F Framebuffer / GPUタイマークエリ**：全パスRGBA8、計測は`performance.mark`ベースです。

### デバッグ表示

開発モード（`npm run dev`、`import.meta.env.DEV`）でのみ、複数パスを持つフィルターを選ぶとサイドパネル下部に「🐛 デバッグ表示」ボタンが現れます（水彩専用だったものを全フィルター対応に一般化しました）。任意の中間パスをプレビューキャンバスへ直接表示でき、「比較サムネイルを生成」で元画像＋各プリセットの並び比較ができます。パスの表示名は `ShaderPassDefinition.label` としてパス定義の隣に置いています（パスIDを鍵にした対応表をパネル側に持つと、パスを増減した瞬間に黙って古くなるため）。ロトスコープの `flow` パスを表示すると、構造テンソルが平坦な肌には反応せず輪郭だけを拾っていることが視覚的に確認できます。本番ビルドではこのコンポーネントごとTree-shakingで除去されます。

## パフォーマンス

- プレビュー解像度は長辺1280px（初期値）に自動縮小し、書き出し時のみフル解像度（既定上限4096px、GPUの `MAX_TEXTURE_SIZE` でも追加クランプ）で再描画します。
- スライダー操作は `requestAnimationFrame` で1フレームに1回へ間引いています。
- シェーダープログラムはフィルター×パスごとに初回コンパイル後キャッシュし、フレームバッファもサイズ単位で再利用します（毎フレーム再生成しません）。
- Playwright + Chromium（ヘッドレス、**SwiftShaderソフトウェアレンダリング**）で1920px幅画像を計測：
  - フィルター切り替え（プレビュー解像度）：全フィルターで1ms未満
  - **実写4K（2160×3840）の等倍書き出し**：シネマティック 約1.5秒 ／ **ビューティーメイク 約2.4秒**（12パス、アイドルプリセット）／ ナチュラル美肌 約4.2秒 ／ ロトスコープ 約6.6秒
  - ビューティーメイクが12パスありながら美肌より速いのは、帯域パスに `maxOutputLongEdge` を掛けているためです（帯域の半径は顔幅比なので、解像度は精度にしか効きません）。この数値は `tests/e2e/visual-reference.spec.ts` が毎回 `[timing]` として出力します
  - ロトスコープは当初20秒かかっていました。異方性Kuwaharaが1サンプルごとに8セクタ全てをループしていましたが、1サンプルは必ず**隣接2セクタにしか寄与しない**（三角重みが1の分割になっている）ため2回に削減し、出力を一切変えずに約3倍高速化しています。
  - いずれも要件（初回表示5秒以内、フィルター処理1〜5秒以内）を満たしています。ただし計測環境はGPUハードウェアが無く**SwiftShader（CPUソフトウェアラスタライザ）** 上での実行のため、実機のGPUハードウェアアクセラレーション環境（本アプリの想定対象）ではこれより大幅に高速になります。
- `performance.mark("filter-render-start"/"filter-render-end")` を計測しているため、実機のChrome DevTools Performanceパネルでも `filter-render` という名前の計測区間として確認できます。フルHD書き出しの実測は、実際にGPUアクセラレーションが有効なChrome/Edgeでダウンロード操作を行い、DevTools Performanceパネルで確認してください。

## 実装方針・既知の制約

- **タイル処理は未実装**：4096px出力がGPUの `MAX_TEXTURE_SIZE` を超える場合は、そのGPU上限まで書き出しサイズを自動的に縮小します（`resolveExportSize` がクランプ）。現行の一般的なGPUは`MAX_TEXTURE_SIZE`が8192px以上のため実運用上は問題になりにくく、優先順位（3. フルHD級の解像度維持 > 6. UIの装飾）に従い、タイル分割処理は実装していません。
- **アップスケールはしない**：「長辺1920px」「長辺1280px」プリセットは、元画像がそれより小さい場合に拡大はしません（画質劣化を避けるため）。
- **Canvas 2Dフォールバックは実装していません**：WebGL2非対応環境では明確な非対応メッセージのみを表示します（優先順位1〜4を優先し、優先順位6のUI充実度は簡略化しました）。
- **PWA**：Service Workerによる静的アセットの最小キャッシュ（ネットワーク優先・オフライン時キャッシュへフォールバック）を実装し、新バージョン検知時は再読み込みを促すバナーを表示します。ビルド出力のプリキャッシュ・マニフェスト自動生成ツールは使用せず、依存追加を避けています。
- **EXIF Orientation**：`createImageBitmap` に依存せず自前のバイナリパーサで読み取り、Canvas 2D変換で焼き込んでいます（ブラウザ間の `imageOrientation` 既定値差異を避けるため）。
- **HEIC非対応**：仕様どおりMVP対象外です。
